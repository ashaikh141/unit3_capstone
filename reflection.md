# Shared Tool Registry: Reflection

For the third question, "How many active projects do we have and what's our onboarding process?", suggest_tool did not return a single tool name. Claude correctly recognized that the question needs both sources and began replying "Both tools are needed: sql_agent → How many active projects do we have", but this broke the required format ("Reply with only the tool name") and was cut off by the 20-token limit before it named retrieval_agent. My validity check flagged it as "NOT a registered tool name", and if the string had been passed to call_tool, it would have returned "Unknown tool" and the user would have received no answer at all. So the model's understanding was right, but the system around it had no way to act on it: the router's interface allows exactly one tool name, and the question genuinely needs two. Better prompting alone would only partly fix this. I could add an explicit "both" option and validate the reply against the registry, which would stop the crash. But a question like this still needs both tools to run and their results to be combined into one answer, which is a fundamentally different approach: classify the question as sql, retrieval, or both, call every tool the route requires, then synthesize the results with attribution to each source. That is what tomorrow's LangGraph orchestrator does with its classification, tool, and synthesis nodes. Two smaller lessons also came out of this: always validate model output against the allowed values before acting on it, and set max_tokens with enough headroom that a reply can't be truncated into an invalid answer.
